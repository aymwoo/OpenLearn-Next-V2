# Release Notes v0.7.3

**发布日期**: 2026年10月25日

OpenLearn V2 **v0.7.3** 是平台的**数据库结构终检与测试隔离补丁版本 (Schema Golden Final Check & Test Isolation Patch)**。本版本收口四类问题 —— 一类是**启动期结构校验缺失**（迁移台账追平 ≠ 库结构正确；用未来备份恢复旧代码时平台仍会带着「比代码新」的结构启动），一类是**测试进程污染生产数据**（`BACKUP_DIR` 未被隔离，测试的迁移前快照与还原安全副本直接写进生产 `backups/`），一类是**CLI 路径上的权限基线缺口**（`cli-data.mjs` 走自己的一套备份实现，产物仍按默认 umask 落盘 644、备份目录 755），一类是**无障碍门禁不可靠**（全局 toast 说明文字在入场动画期间跌到 WCAG AA 以下；无障碍门禁因浮层残留而在「单跑绿 / 全量跑红」之间摇摆）。同时修正五处「照文档操作会出事故」级文档失实，并把 #294/#295 引入的门禁债务连同**生成器根因**一起修掉。

> **v0.7.2 → v0.7.3 共 11 个提交**，跨 23 个文件。

## 一、启动期结构金样终检与严格台账防降级

此前「迁移台账追平」就被当作「库结构正确」—— 台账记着「迁移已应用」并不代表库里真有那些表和列；用未来备份恢复旧代码（降级）时，平台会带着一个「比代码新」的结构继续启动。

1. **严格台账防降级**：两个启动入口（`server.ts` 与 kernel `initializeDatabase`）均以 `strictLedger: true` 调用 `runMigrations` —— 台账里存在、但迁移目录中已不存在的条目即 **FATAL**，报错同时指出「用未来备份恢复了旧代码（降级）」与「已应用迁移被改名」两种成因。有意的降级运维可用 `MIGRATION_ALLOW_UNKNOWN_LEDGER=true` 显式放行。库函数默认**不拦** —— 迁移子集调用是升级演练（v034/v036/v061）的合法用法。
2. **schema 金样终检**：新增 `migrations/schema-golden.json`（空库跑完全部 44 个迁移后的表→列快照，随包发布，改迁移后用 `pnpm db:gen-golden` 重新生成）。`assertSchemaMatchesGolden` 在两个启动入口迁移后校验：**实际库缺金样声明的表/列 → FATAL 并列出缺在哪**；多出的表/列（插件自建表、expand-contract 过渡列）不报错。金样文件缺失 = packaging 级 FATAL（与 #283 漏发 `migrations/` 同类故障）。
3. **配套测试**：新增 `schema-golden.test.ts`（金样对账 —— 改迁移忘再生成**立刻红**并提示跑 gen / 整表缺失 / 列缺失（DROP COLUMN）/ 多余结构合法 / 金样缺失报错 / 严格台账 FATAL-放行-子集合法三态）；新增真实迁移链 **DOWN 烟雾测试**（回滚 → 重放 → 金样对账），钉住「DOWN 脚本不静默烂掉」。

## 二、测试进程不再污染生产备份目录

1. **现象（实测）**：`migrate-safety` / `cli-data-restore` / `cli-enhanced` 三条用例报「备份目录不存在」而变红；同一时间生产 `backups/` 下多出 `pre_migration_*.db` / `pre_restore_*.db`（全是测试库残骸）。
2. **根因**：本地开发机常把 `BACKUP_DIR` 导进 shell 环境，而 `packages/core/db/migrator.ts` 与 `cli-data.mjs` 都是 `process.env.BACKUP_DIR || <默认目录>` 的写法。`vitest.setup.ts` 此前只清了 `OPENLEARN_DB_PATH`（Issue #194）、重定向了 `OPENLEARN_DATA_DIR`，**唯独漏了 `BACKUP_DIR`**。
3. **改法**：在 `vitest.setup.ts` 的隔离块里与 `OPENLEARN_DB_PATH` 并列地 `delete process.env.BACKUP_DIR`，并在控制台显式告知（不静默吞掉）。选择「清除」而非「改写成临时路径」—— 该变量的读者语义各不相同（`server/utils/paths.ts` 的 `getBackupsDir`、`cli-data.mjs` 的 `runRestore`、`scripts/site-backup.mjs`），改写会让某些读者指向语义不对的目录；用例自己 `set` 的值仍生效（setup 先于用例运行）。

## 三、CLI 备份/还原产物的权限硬化

1. **问题**：v0.7.2 引入的 `packages/core/db/secure-files.ts` 只覆盖内核侧的 `backup-manager.ts` / `migrator.ts`；`cli-data.mjs` 走的是**自己的一套**实现 —— `createSafetySnapshot()` 用 `VACUUM INTO` 落盘、`copyFileSync` 冷备、暂存文件 rename 成主库，这些产物全按默认 umask 落盘（实测 644），备份目录按 `mkdirSync` 建为 755。
2. **改法**：在 `cli-data.mjs` 内联 `hardenFile()` / `ensureSecureDir()`（口径与 `secure-files.ts` 一致：目录 700、文件 600、**只收紧不放宽**、Windows 忽略），应用到冷备、整包备份、还原安全副本、暂存文件与还原后的主库。
   > **为什么内联而不 import**：CLI 必须能在**发布包**里独立运行，而发布清单只有 `cli-*.mjs` 与 `dist/*.cjs`，源码里的 `secure-files.ts` 并不存在 —— 与 `loadCliMigrator` 踩的是同一个坑。
3. **测试**：`scripts/__tests__/cli-data-restore.test.ts` 新增 1 例，断言还原产物权限合规（安全副本 600、备份目录 700、还原后主库 600）；已用「撤掉硬化」的**反证**确认它会变红。

## 四、无障碍：toast 对比度与门禁的顺序依赖

1. **现象（实测，非推断）**：用 axe + 逐帧采样定位到违规元素是全局 toast 的说明文字 `<p class="text-xs text-gray-500 dark:text-gray-400">`。`e2e/a11y-gate.spec.ts` 单跑 5/5 通过，全量跑则报出一条「测评中心存在 color-contrast 违规」。
2. **根因（两层）**：
   - toast 整块带 `motion` 透明度淡入淡出。axe 按元素不透明度混合前景/背景 —— 实测入场动画经过 opacity **0.26 / 0.4 / 0.55** 时，说明文字的实际对比度跌到 4.5:1 以下，即「刚弹出来的那 0.3 秒」里次要说明文字**不可读**。颜色余量本身也太薄（浅色 4.83:1 / 深色 7.03:1）。
   - toast 是**全局**浮层且由**上一个工作区**的动作触发（进入「互动课堂」会自动锁定全班并弹一条「🔒 锁状态更新」），而 SPA 的 hash 路由切换**不重新加载页面**（`page.goto('/#/x')` 在只改 hash 时是同文档导航），于是它跨工作区残留，并恰好在下一个工作区的扫描窗口里入场。`freezeAnimations()` 只冻结 CSS 动画/过渡，**挡不住 `motion.js`**（它用 rAF 直接改 style）—— 这是原先的漏网原因。
3. **改法**：文字改用 `text-gray-600 dark:text-gray-300`（浅色 **7.56:1** / 深色 **12.1:1**），并**去掉透明度淡入淡出**，只保留位移与缩放 —— 文字全程以完整不透明度渲染；`a11y-gate.spec.ts` 新增 `settleOverlays()`，扫描前等浮层不透明度归位，既保留「toast 自身也要合规」的覆盖，又让门禁不再依赖 toast 出现的时机。
4. **测试**：新增 `src/features/shared/__tests__/ToastContainer.a11y.test.tsx`（3 例：浅色 ≥ 7:1、深色 ≥ 10:1、无透明度淡入）—— 这是**确定性**单元门禁，不依赖浏览器采样时机。已用「把颜色改回 `gray-500`/`gray-400`」的**反证**确认它会变红。

## 五、文档：修正五处「照文档操作会出事故」级失实

全库文档一致性审计（86 篇内容级核查）的第一批修复 —— 这五处不是措辞瑕疵，而是**照着做就会出事故**：

| 文档                           | 问题                                                                            | 危害                           |
| ------------------------------ | ------------------------------------------------------------------------------- | ------------------------------ |
| `admin-manual.md:345`          | 容器卷要求挂 `/app/packages/core/db` —— **实际是 `/data`/`/backups`**，方向写反 | 照做重启丢全部数据             |
| `admin-manual.md:273`          | `OPENLEARN_DB_PATH` 容器路径停在旧 `/app` 布局                                  | 与同文 §6.4 自相矛盾，误导排障 |

| `version-migration.md:135/141` | 「checksum 仅记录不校验」—— 实际每次启动都比对                                  | 掩盖真实存在的保护机制         |

## 六、CI 门禁：修掉 #294/#295 引入的债务，并修生成器根因

1. **问题**：#294、#295 是**带着失败的检查被合并**的 —— main 的 Format check（格式基线棘轮）与 typecheck-and-test（ESLint 告警预算）两个作业连续两次 push 转红。格式不合规 5 个文件；ESLint 6246 > 基线 6243。
2. **定位**：逐文件比对基线树与合并后的树，精确锁定 3 条**新增**告警（`schema-golden.ts` 抛错未带 `cause`、`gen-schema-golden.ts` 与 `migration-down-smoke.test.ts` 各一处未使用 import），净增 3 = 6246 − 6243，与实测吻合。
3. **修法 1（格式根因）**：4 个新文件直接 prettier；但 `migrations/schema-golden.json` 是**生成物** —— 生成器写 `JSON.stringify(x, null, 2)`（短数组全展开）而 prettier 把短数组折成单行，手工格式化只是把「生成 → 不合规 → CI 红 → 手改 → 再生成又红」的死循环往后推一轮。因此把**生成器**改成用 prettier 按 `.prettierrc` 排版输出，**生成即合规**，prettier 成为排版的唯一来源。
4. **修法 2（ESLint）**：删掉两处未使用 import；金样解析失败改为 `throw new Error(..., { cause: err })` —— 既过 `preserve-caught-error`，也真正保住根因异常。
5. **验证**：格式门禁不合规 0 个；ESLint 6243 = 基线 6243（不新增欠债）；重跑 `pnpm db:gen-golden`，生成物 `prettier --check` 通过且与提交版仅差 `generatedAt` 一个字段（**根因反向验证**）；格式化后的金样 JSON 与格式化前语义完全等价，严格 `JSON.parse` 可解析（82 表、无尾逗号）。
6. **顺带封掉版本一致性门禁的一个盲区**：原断言 1 拿 `PLATFORM_VERSION` 与 `package.json.version` 比 —— 而 `PLATFORM_VERSION` 正是**运行时从 package.json 读出来的**，两者同源，**恒等**，无论 `packages/core/version.ts` 里的 `FALLBACK_VERSION` 字面量写成什么都不会红（实测：字面量停在 `0.7.2`、package.json 已是 `0.7.3` 时，6 例断言依然全绿）。而该字面量在**无法定位平台 package.json** 时（只拷了 `dist/` 的部署方式）就是对外展示的版本号。现新增断言 2b 直接读源码抠出字面量比对，并做了**反向验证**：字面量改成 `0.0.1` → 精确报「版本漂移拦截」；改回 → 7 例全绿。

## 七、验证与升级说明

1. **验证**：`pnpm lint`（`tsc --noEmit`）与 `pnpm lint:strict` 均 0 error；ESLint 告警预算 6243 条（未超基线）；格式基线棘轮不合规 **0** 个；源码编码检查与 i18n 检查通过；文档漂移审计 0。
   - **全量单测的基线对照**：本机 node_modules 的 better-sqlite3 ABI 已随环境漂移到 Node 26，在此环境下全量套件有 **72 例**失败（67 例为 jsdom `localStorage` 未定义的环境噪声）。为区分「环境噪声」与「真实回归」，在**同一 Node 26、同一 base commit（`9d0324b`）**下对未改动的基线树跑同一套件并逐条比对失败集合：两侧**失败集合完全相同（72 例，零新增、零差异）** —— 这些失败与 v0.7.3 改动无关。CI（Node 22 干净安装）是权威结论。
   - **版本一致性门禁 7 例通过**（0.7.3）。
2. **发布形态自检（消费者视角全链路实测）**：
   - `bash scripts/publish.sh --dry-run` 全流程通过，发布清单核对四项全过：`version=0.7.3` / `sdk=3.7.0`（精确 pin）/ `preloadInFiles=true` / `preloadExists=true`；产出 `openlearn-next-0.7.3.tgz`，**115 个文件**（比 v0.7.2 多 1 个 = 新增的 `migrations/schema-golden.json`）。
   - 按 `files` 清单还原包并模拟真实消费（把 SDK pin 改写为精确版本后打包 → 新建空项目 `npm install <tarball>` → **586 个包装成功**）→ 启动 → `[Platform] Ready`、`[SchemaGolden] 启动终检通过`、`OpenLearn Next v0.7.3 ready`、`GET /` 返回 **HTTP 200**。
   - 迁移目录从**包根**正确解析（`[DB SSOT] 迁移已就绪（44 个文件，目录 <pkg>/migrations）`）；权限基线在全新实例上即合规：主库 **600**、备份目录 **700**、`pre_migration` 快照 **600**。
3. **迁移**：本版本**不含新增迁移文件**（沿用 v0.7.2 的 44 个 `.sql`）；新增的是 `migrations/schema-golden.json` —— 它是**快照文件而非迁移**，由 `pnpm db:gen-golden` 生成，随包发布。
4. **行为变化（请留意）**：
   - **启动可能因结构不符而失败**：实际库缺少金样声明的表/列 → 启动 FATAL 并列出缺在哪。这是**有意的 fail-fast** —— 与「带着残缺结构继续服务」相比，早失败更安全。若确实是有意的结构变更，先在测试环境跑 `pnpm db:gen-golden` 更新金样并走 PR 评审。
   - **降级会被拦**：台账里有、迁移目录里没有的条目 → 启动 FATAL。有意的降级运维请显式设置 `MIGRATION_ALLOW_UNKNOWN_LEDGER=true`。
   - **金样文件必须随包发布**：`migrations/schema-golden.json` 缺失 → 启动 FATAL（packaging 级故障，与 #283 同类）。
5. **运维**：`cli-data.mjs` 的备份/还原产物现在**创建即 600 / 目录 700**。既有部署里的历史 644 备份可用 `pnpm ops:check-perms --fix` 一次性回补。
6. **插件作者**：本版本未改动 `@openlearn/plugin-sdk` 的公开类型（SDK 版本独立发布，当前仍为 3.7.0）。`engines.openlearn` 约束为 `>=0.2.5` 的内置插件对 0.7.3 全部兼容。
