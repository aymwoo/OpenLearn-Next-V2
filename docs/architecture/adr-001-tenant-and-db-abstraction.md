# ADR-001：多租户 / 多校区与数据库抽象层

- **状态**：Accepted（2026-10-18）
- **决策**：一校一实例（单库单租户），多校通过多容器 / 多库部署；不引入 `school_id` 横切改造；短期内不引入 ORM / 数据库抽象层。
- **关联**：Issue #149、#151（配置分层）、#150（按实例观测与恢复演练）

---

## 1. 背景与事实

在 Issue #149 提出时，代码库的事实基础如下（均已在本仓库核实）：

| 事实                                      | 证据                                                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 当前是单实例单校模型                      | `server/`、`packages/`、`migrations/` 中搜索 `tenant` / `school_id` / `campus` 无业务实现                          |
| 数据库为 SQLite（better-sqlite3）         | `package.json` 依赖；`packages/core/db/migrator.ts`                                                                |
| 插件可直接写 SQL                          | `ctx.db.ensureTable()` / `ctx.db.table()` / `resolve(IDatabaseToken)`；`plugin-host/sql-guard.ts` 只做表前缀白名单 |
| 迁移与备份按「一个库」设计                | `_migrations`、`VACUUM INTO` 迁移前快照、`pre_migration_*.db`、`site-backup.mjs`                                   |
| 部署形态是「一个应用进程 + 一个数据目录」 | `docs/deployment/production-guide.md`、`docs/deployment/docker-nginx.md`、`Dockerfile` 的 `OPENLEARN_DATA_DIR`     |
| 插件私有表按「安装 UUID」建表             | `plugin_table_prefix()`；插件迁移记录存 `plugin_declared_migrations(plugin_id, …)`                                 |

这些事实意味着：引入 `school_id` 不是加一列，而是要同时改核心表、插件表前缀、插件 SDK、所有已装插件的 SQL 与迁移，以及备份/恢复语义。

## 2. 决策

### 2.1 部署模型：一校一实例

- **一个学校 = 一个平台实例 = 一个数据库 = 一个数据目录**。
- 多校部署通过「多容器 / 多进程 / 多主机」实现，每个实例完全独立：
  - 独立 `OPENLEARN_DATA_DIR` / `OPENLEARN_DB_PATH` / `BACKUP_DIR`；
  - 独立 `ENCRYPTION_KEY`（绝不共用，否则 AI Provider 凭据与该实例的加密边界被拉平）；
  - 独立端口与域名（反向代理按 Host 路由）。
- **不做**跨实例的账号互通、跨校班级、跨校实时协作、跨库联合查询；跨校统计通过离线导出 / ETL 聚合。

### 2.2 数据模型：不做 `school_id` 横切

- 核心表、插件表都不增加租户列。
- `plugin_config` 的 `scope_type='school'` 保留为**枚举位**（Issue #151 已实现解析逻辑），但在一校一实例下没有自动来源：单实例内「学校层」等价于平台层，不需要额外写入。
- 任何新代码不得引入跨校共享状态（全局缓存键、共享存储桶、共享队列、跨库外键）。

### 2.3 数据库：继续使用 SQLite，不引入抽象层

- 继续以 better-sqlite3 + 原生 SQL 作为唯一数据访问方式。
- **不引入 ORM、不引入查询构建器、不承诺 PostgreSQL 兼容**。
- 保留并稳定现有 `IDatabase` / `ctx.db` 接口（`ensureTable` / `table` / `prepare().run/get/all` / `migrate`），这是插件生态的公共契约。

## 3. 理由

1. **写并发模型**：SQLite 单写者。多校共库会把各校的写操作放进同一个写锁，开学季/考试季的峰值互相拖慢；一校一库把写竞争限制在校内。
2. **隔离与合规**：学生个人数据、成绩、考勤天然按校隔离。一实例一库是「物理隔离」，比任何 `WHERE school_id = ?` 中间件都更难绕过 —— 后者只要有一条漏写条件的 SQL 就是跨校泄露。
3. **备份 / 恢复 / 回滚粒度**：现有 `VACUUM INTO` 快照、`pre_migration_*.db`、`restore --snapshot`（Issue #150）都按「一个库」工作；一校一实例让这些机制直接按校生效，无需重写。
4. **插件生态成本**：插件私有表、迁移版本、存储键都以 `plugin_id` 为维度；引入租户列需要改插件 SDK 与所有第三方插件，属于破坏性变更，收益（SaaS 多租户）当前并未出现。
5. **部署成本可控**：多校场景的现实形态是「各校独立采购/独立运维」。多容器部署在 Compose / 反向代理层面已经成熟，新增成本主要是运维规范而非代码改造。
6. **数据库抽象收益不明**：当前 SQL 深度依赖 SQLite 特性（`VACUUM INTO`、WAL、`json_extract`、`sqlite_master`、`ON CONFLICT`、`PRAGMA`）。在没有明确的 PostgreSQL 需求前，抽象层只会增加一层薄封装与调试成本。

## 4. 代价与缓解

| 代价                  | 缓解                                                                                                                  |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 每校一套升级/备份流程 | 复用 `docs/deployment/multi-school.md` 的逐实例清单；升级回归门禁（Issue #147）与恢复演练（Issue #150）按实例模板执行 |
| 跨校报表需要额外管道  | 统一导出格式（`site-backup` / `snapshot` + 只读副本），在离线数仓聚合；不在线联邦查询                                 |
| 无法跨校共享账号      | 明确不支持；如需统一身份，走外部 IdP 单点登录（未来独立评估）                                                         |
| 资源利用率低于共享库  | 单实例资源可按校配额；空闲实例可降配                                                                                  |

## 5. 数据库抽象层评估结论

**结论：暂不引入。**

- 现在需要的不是「换数据库」，而是「插件 SQL 不越界」：已有 `sql-guard` 表前缀白名单、`ensureTable` 表名白名单、插件迁移事务与 checksum 校验。
- 引入受限 DAO / 查询构建器会迫使所有第三方插件重写数据访问，属于破坏性变更；在没有第二数据库目标前收益为零。
- 保留两条**触发条件**，满足任一再重新评估：
  1. 出现必须使用 PostgreSQL 的部署需求（例如托管 SaaS、跨实例共享写、需要行级安全策略）；
  2. 单实例写入成为瓶颈，且分库/分片无法解决（例如单校并发写持续打满 WAL）。
- 若未来引入，推荐路径是「旁路新增」而不是「原地替换」：新增 `IDatabase` 的可选查询构建器实现，插件按需迁移，原生 SQL 接口长期保留。

## 6. 何时重新评估本 ADR

出现以下任一情况时，重开本决策（新 ADR 覆盖）：

- 需要「一个部署服务多所学校」的托管 SaaS 商业模式；
- 跨校统一报表/统一身份成为硬需求，且离线聚合无法满足时效；
- 单实例规模超出 SQLite 的写吞吐（以 `openlearn_plugin_*` 与迁移时长指标为依据）；
- 插件生态要求跨校共享一组插件数据。
