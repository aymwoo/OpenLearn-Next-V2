# 功能巡检（sweep）

> 把「把所有功能点一遍」从一件需要人盯着的苦差事，变成一条命令。
>
> ```bash
> pnpm sweep
> ```

## 它解决什么问题

手工验收一个教学平台的全部功能，流程是这样的：登录教师 → 逐个菜单点 → 每个弹窗
都开一遍 → 退出 → 登录学生 → 再点一遍 → 再登录一个学生再看一遍。

这个流程有三个硬伤：

1. **点漏了不知道自己漏了** —— 没有清单，就不知道覆盖是否完整；
2. **坏在哪说不清** —— 看到白屏，只知道「这个功能坏了」，不知道是 JS 抛异常、
   还是接口 500、还是某个数据缺失；
3. **不可重复** —— 下次改完代码，没人愿意再手点一遍。

`sweep` 把这三件事都自动化了：**自动枚举**所有入口、**自动分类**故障类型、
**一条命令**可重复执行。

## 快速开始

```bash
pnpm sweep                   # 完整巡检（起临时演示库 → 全角色巡检 → 出报告）
pnpm sweep -- --roles teacher   # 只巡检教师端
pnpm sweep -- --no-fail      # 即使有错误也返回退出码 0
```

产物：

```
artifacts/sweep/
├── report.md          # 人读的：概要 + 明细表 + 问题详情（可直接贴进 issue）
├── report.json        # 机器读的：可接 CI 门禁 / 趋势对比
├── server.log         # 演示服务器日志
└── screenshots/       # 每个视图一张截图
```

## 工作原理

### 1. 不碰登录页

登录走真实 API，把会话 Cookie 直接注入浏览器上下文：

```
POST /api/auth/login  {entrance: 'teacher', username, password}
  → Set-Cookie: edu_os_token=…
  → context.addCookies(...)
```

页面加载后就是已登录状态。**巡检全程不需要填任何登录表单**，也不受改密门影响。

### 2. 导航项在运行时发现，不写死清单

教师/管理员工作台是单一 SPA + hash 路由（`src/utils/teacherTabHash.ts`），
侧边栏每个导航按钮都带 `aria-label`。因此巡检工具**直接读 DOM 发现导航项**再逐个点击：

```ts
const labels = await sidebar.locator('button[aria-label]').evaluateAll(/* … */);
```

新增导航项、插件页签会自动被纳入巡检，不需要改清单 —— 这是「点漏了不知道自己漏了」
的根治办法。

### 3. 前置数据按需补齐

有些功能**没有数据就根本进不去**：

| 功能 | 前置条件 |
| --- | --- |
| 学生端「查看待办作业」 | 班级里有一份已发布作业 |
| 学生端「进入实时课堂」 | 有一节进行中的课堂会话 |
| 教师端「授课驾驶舱」 | 同上，且会话处于授课阶段 |

巡检会在对应轮次前用 API 补齐这些数据（`scripts/sweep/prepare.ts`），全部落在
**一次性演示库**里。

### 4. 轮次顺序是有讲究的

巡检分成 5 轮，顺序不是随便排的：

| 轮次 | 角色 | 数据状态 | 覆盖到什么 |
| --- | --- | --- | --- |
| 1 | 管理员 | 无课堂会话 | 管理后台；**无会话时的冷启动缺陷** |
| 2 | 学生 | 无课堂会话 | 仪表盘 / 我的测评 / 我的作业 / 课程内容 |
| 3 | 学生（课中） | 会话 @课前就绪 | 「进入实时课堂」入口 + 课中视图 |
| 4 | 教师 | 会话 @课前就绪 | 教师工作台全部视图与二级页签 |
| 5 | 教师（授课中） | 会话 @授课中 | 完整授课驾驶舱 |

两个必须记住的约束：

- **有进行中的课堂会话时，学生端会被锁进课中视图**，仪表盘挂件全部不可见
  → 所以「常态学生外壳」和「课中学生外壳」必须分两轮测。
- **教师打开互动课堂会开启「全课专注锁定」**，学生端随即被锁定
  → 所以学生的课中轮次必须排在教师轮次**之前**。

### 5. 全局问题与视图问题分开

有些问题在**每个**视图里都会冒出来。典型：无课堂会话时前端仍去 POST
`/api/classroom/sessions/:lessonId/view-state`，于是每次进系统都拿一个 404。

如果把它们算到每个视图头上，报告的信噪比就废了 —— 真正「这个视图坏了」的信号
会被淹没。因此报告会先把问题分成两类：

- **全局问题**：启动期探针抓到的，或在某个角色 ≥70% 视图里都出现的
  → 单独成节，**不计入各视图成败**；
- **视图问题**：其余 → 逐视图列出，并计入成败判定。

## 判定标准

| 状态 | 含义 |
| --- | --- |
| ✅ 正常 | 该视图没有抓到任何错误/告警 |
| ⚠️ 告警 | 有 4xx 或请求失败，但没有崩溃级错误 |
| ❌ 错误 | 有未捕获异常、console.error 或 5xx |
| ⭕ 未找到 | 入口没找到（角色限制/文案变更），**不计缺陷** |

退出码：有 ❌ 时返回 1，否则 0（`--no-fail` 可强制返回 0）。

## 命令行参数

| 参数 | 说明 |
| --- | --- |
| `--port <n>` | 一次性演示服务器端口（默认 9300） |
| `--base-url <url>` | 巡检已在运行的服务（给出后不启动演示服务器、不重建演示库） |
| `--out <dir>` | 产物目录（默认 `artifacts/sweep`） |
| `--roles <list>` | `admin,teacher,student,student-live,teacher-live` |
| `--keep-db` | 保留现有演示库，不重建 |
| `--no-fail` | 即使发现错误也返回退出码 0 |
| `-h, --help` | 帮助 |

## 数据环境

默认在**独立的一次性数据库** `storage/demo.db` 上跑，完全不碰开发库
`packages/core/db/educational_os.db`。数据由 `scripts/dev-demo.ts` 播种
（演示教师 / 2 个班级 / 12 名学生 / 1 门课程 / 1 条课表）。

服务器以 `PLAYWRIGHT_TEST=1` 启动：

- 种子口令等于用户名（`admin/admin`），且 `must_change_password = 0`
  → 不必去读随机口令文件，也不会被改密门拦住；
- 登录 / 写入限流放宽 → 巡检不会把自己锁在门外。

该环境变量**仅用于本机的一次性演示库**。仓库已有
`packages/core/db/__tests__/playwright-test-production-guard.test.ts`
断言 `NODE_ENV=production` 下必须拒绝启动。

## 与 `e2e/` 下的 Playwright 套件的区别

| | `pnpm test:e2e` | `pnpm sweep` |
| --- | --- | --- |
| 形态 | Playwright test runner | 独立脚本 |
| 目的 | **断言**「功能必须这样表现」 | **发现**「哪里坏了」 |
| 覆盖 | 手写的关键旅程 | 自动枚举的全部入口 |
| 失败时 | test failed，CI 变红 | 出一份可读的缺陷报告 |
| 适合 | 防回归 | 验收 / 摸底 / 大版本自检 |

两者互补：先用 sweep 摸清现状，再把高频路径固化成断言式回归测试。

## 扩展巡检范围

想覆盖新的视图 / 角色，改 `scripts/sweep/manifest.ts`：

- **教师/管理员的新导航项** —— 不用改，运行时自动发现；
- **新的二级页签** —— 在 `SUB_TABS_BY_TAB` 里登记 `{id, label, name}`;
- **学生端的新视图** —— 在 `STUDENT_TARGETS` 里加一条 `{id, label, path, click}`;
- **新的角色** —— 在 `SWEEP_ROLES` 里加一条（注意轮次顺序与「全课专注锁定」的约束）。

## 已知限制

- 只覆盖 Chromium（仓库现有 e2e 套件同样如此）。
- 巡检**只读不写**：命中「删除 / 清空 / 发布」等危险词的按钮一律不点。
- 动态注册的插件页签若不带 `aria-label`，发现机制可能扫不到 —— 这类入口
  会在报告里表现为「未找到」，可按需手工补进清单。
